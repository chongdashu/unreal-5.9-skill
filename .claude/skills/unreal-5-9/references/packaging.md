# Packaging: a standalone Mac app and an iOS build

Verified on the Epic launcher's 5.9.0 on a Mac (Xcode 26.2), packaging a C++ project for the first time. The iOS app was then installed and run on an iPhone 15 Pro Max (iOS 26.6); an iPad Air (M4) on iPadOS 27 got as far as signing. Names starting `game.` stand in for the game's console variables: choose your own.

## 1. Packaging and running a Mac app

- **The command.** `Engine/Build/BatchFiles/RunUAT.sh BuildCookRun -project=<abs .uproject> -platform=Mac -clientconfig=Development -build -cook -stage -pak -nop4 -utf8output -unattended` (add `-package` and use `-platform=IOS` for iOS). The cook alone took 4 to 14 minutes here. It compiles the editor module too, so close the editor on that checkout or use a worktree.
- **Content loaded by name is not packaged.** A game that finds its art with `LoadObject` and path strings gives the cooker nothing to follow. Add `+DirectoriesToAlwaysCook=(Path="/Game/<folder>")` (and `/Engine/BasicShapes` if the code loads the engine's cube or plane) and `+MapsToCook=(FilePath="/Game/Maps/<map>")` under `[/Script/UnrealEd.ProjectPackagingSettings]` in `DefaultGame.ini`.
- **The app to run is the staged one.** `Saved/StagedBuilds/Mac/<Project>.app` holds the content (under `Contents/UE`). The copy `-archive` writes, and `Binaries/Mac/<Project>.app`, are the program alone: they exit at once with "Failed to open descriptor file".
- **Run it from a shell with `-stdout -FullStdOutLogOutput`** and read the log from the pipe. `-abslog` wrote nothing.
  - The Development app is sandboxed, so its `Saved` folder is under `~/Library/Containers/<bundle id>`, and a `find` there from the terminal hung until stopped.
  - For files the game writes, make an unsandboxed copy: `cp -Rc` the staged app, then `codesign --force --deep -s -` on the copy (no entitlements). It then saves under `~/Library/Application Support/Epic/<Project>/Saved`.
  - The first launch of a fresh copy printed nothing for over 30 s; the second ran normally.
- **A screenshot from a packaged game.** No editor, so no capture tool. A game CVar that calls `FScreenshotRequest::RequestScreenshot(true)` once after N seconds (`game.Test.ShotAfter` here), set with `-ExecCmds="game.Test.ShotAfter 12"`, wrote `Saved/Screenshots/Mac/ScreenShot00000.png` at the window's size. `-ExecCmds` values arrived about 3 s after the map loaded, so a CVar read once at BeginPlay misses them. Several commands are separated by commas.
- **Nanite meshes went grey in the packaged game, not in the editor.** The log said "Material ... missing usage flag Nanite! Default Material will be used in game" for 16 materials.
  - The glTF importer turns Nanite on for every static mesh (62 of 62 here, 54,000 triangles in all) and parents every material to `/InterchangeAssets/gltf/M_Default` through `MI_Default_Opaque_DS`; that engine material has no Nanite flag, the editor sets it in memory, and a cooked game cannot.
  - Fix used: duplicate both engine assets into the game, `MaterialEditingLibrary.set_material_usage(copy, MaterialUsage.MATUSAGE_NANITE)`, and `set_material_instance_parent` the imported instances to the copy (41 instances, 0 warnings afterwards, and a capture of the packaged game showed the court and props in their own colours).
  - Turning Nanite off on the meshes would also do it.
  - Run a packaged build before trusting any look that was only seen in the editor.
- **Editing assets without a window.** `UnrealEditor-Cmd <.uproject> -run=pythonscript -script=<abs .py> -unattended -nosplash -AllowCommandletRendering` ran a script that changed and saved materials. With `-nullrhi` it failed: "this editor has no renderer, so materials can't be compiled". Neither `print` nor `unreal.log` reached the redirected output; write results to a file from the script. A Python error gives exit code 255.
- **Keep the agent plugins out of the game.** `ModelContextProtocol` has Runtime modules. Give it, `AllToolsets` and `PythonScriptPlugin` `"TargetAllowList": ["Editor"]` in the `.uproject`; the editor still loads them.

## 2. Building and signing for iOS

- **iOS needs the launcher's iOS option.** Without it `Engine/Binaries/IOS` does not exist. Epic Games Launcher, Library, the arrow beside Launch on the engine, Options, iOS; the editor must be closed.
- **The Mac's renderer (Metal SM6) cannot be built for iOS from the launcher install.** `bSupportsMetalMobileSM6=True` (Experimental; A17 Pro or M2 and newer) makes the build unzip `Engine/Binaries/ThirdParty/Apple/MetalShaderConverter/IOS/libmetalirconverter.embeddedframework.zip`, which the install does not contain: "Result: Failed (OtherCompilationError)".
  - `MetalShaderConverter.build.cs` only asks for it when bindless is on, but with `[ShaderPlatformConfig METAL_SM6_IOS] BindlessConfiguration=Disabled` the cook died with 366 errors in the engine's TSR shaders (`int16_t2` unknown).
  - A forum thread reports the same missing file on 5.8.
  - So no Lumen, Nanite, Virtual Shadow Maps or ray tracing on iOS from this install.
- **Metal SM5 on iOS built.** `bSupportsMetal=False`, `bSupportsMetalMobileSM5=True` under `[/Script/IOSRuntimeSettings.IOSRuntimeSettings]`, and `r.RayTracing=False` in `Config/IOS/IOSEngine.ini` (the project had it on for every platform): 849 packages cooked, 0 errors, a 500 MB `Binaries/IOS/<Project>.app`. Landscape only is the engine's default; `FrameRateLock` defaults to 30.
- **Signing with no new Apple setup.** `CodeSigningPrefix=com.<company>` under `[/Script/MacTargetPlatform.XcodeProjectSettings]` in `DefaultEngine.ini` gives the bundle ID `com.<company>.<Project>`; `CodeSigningTeam=<team id>` in the same section of `Config/UserEngine.ini` (ignored by Git) keeps the team out of the repo. Automatic signing then used the Xcode-managed wildcard profile ("iOS Team Provisioning Profile: *") already on the Mac.
- **A second device needs an Apple account in Xcode.** The wildcard profile on disk covered one device.
  - BuildCookRun's own xcodebuild uses `-destination generic/platform=iOS`, which never registers a device, so the profile stays as it was.
  - Re-running the last xcodebuild line from the UAT log (`UE_XCODE_BUILD_MODE=Package`) with `-destination "id=<device udid>" -allowProvisioningDeviceRegistration` is the route, and it needs an account under Xcode, Settings, Apple Accounts ("No Accounts" otherwise) whose developer agreement is current ("PLA Update available" otherwise; only the account holder can accept it, on developer.apple.com).
  - Not completed here: the agreement was still pending.
- **A device newer than Xcode.** An iPad Air (M4) on iPadOS 27 against Xcode 26.2: pairing worked (`xcrun devicectl manage pair`), the Developer Mode switch appeared in Settings only after pairing, and then the developer disk image would not mount ("The bundle image is missing the requested variant for this device").
  - Xcode, Settings, Components listed "Device Support for iPhone 17e, iPad Air 11-inch (M4), and iPad Air 13-inch (M4)"; the download leaves `~/Library/Developer/Packages/<Xcode build>/XcodeSystemResources.pkg`, which still has to be installed with an administrator password (Xcode asks, or `sudo installer -pkg <that file> -target /`).
  - After that it mounted. No Xcode update was needed.
- **The iOS Simulator is not a way to see the game.** With the launcher install, `Build.sh <Target> IOS Development -architecture=iossimulator` compiles the game module and then fails to link (`library 'ThirdParty/ICU/.../lib/IOS/Simulator/Release/libicu.a' not found`); a source checkout has those libraries. Even then MetalRHI marks SM5 and SM6 "not supported on simulator" and uses the mobile renderer (`SP_METAL_SIM`), so the picture and frame rate say nothing about a device. The failed try leaves empty folders under the engine's `Intermediate/Build/IOS/iossimulator`.

## 3. On the device

- **Putting it on a device without Xcode's window.** `xcrun devicectl list devices`, then `xcrun devicectl device install app --device "<device name>" Binaries/IOS/<Project>.app` and `xcrun devicectl device process launch --device "<device name>" --terminate-existing <bundle id> -- '-ExecCmds="game.Test.ShotAfter 20"'`. The inner double quotes must reach the device: without them the game got `-ExecCmds=game.Test.ShotAfter` and took the stray `20` for a map name ("Failed to enter /Game/Maps/..."; it then loaded the default map anyway). The 500 MB app installed in under a minute and the map was up 3 s after launch.
- **The device must be unlocked with its screen on.** Install fails with `kAMDMobileImageMounterDeviceLocked`, launch with "the device was not, or could not be, unlocked".
  - `xcrun devicectl device info lockState` reports `passcodeRequired: false` for a while after the screen sleeps, and an app launched then is sent to the background within a second ("Application will deactivate" in its log), as it is when the owner switches to another app.
  - Check the log for that line before reading anything into a missing screenshot.
- **Reading the game's files back.** `xcrun devicectl device copy from --device "<name>" --domain-type appDataContainer --domain-identifier <bundle id> --source Documents/<Project>/Saved --destination <folder>` brings the log (`Logs/<Project>.log`) and screenshots; `device info files` with the same domain options and `--recurse` lists them. In zsh, pass each option as its own word: options kept in one variable arrive as a single argument and devicectl prints its usage.
- **What the first device log showed.** About 53 to 60 frames per second on the title screen (from frame numbers and timestamps), and "Temperature Changed: Serious" 14 s after launch. The iPhone15ProMax device profile sets `r.MobileContentScaleFactor` to 2, so the backbuffer is 1864 x 860 on a 2796 x 1290 screen; safe-area numbers the engine reports are in those pixels (see the safe-area entry in `hud-and-input.md`, section 5).
- **Measuring frame rate on a device.** Pull the log back and divide the frame counter in the `[frame]` column by the timestamps, stopping at the first "Application will deactivate": a run where the owner touched the phone is not a measurement. Wait a few seconds before copying, or the log's tail is not flushed.

## 4. The look on iOS

- **Why the phone looked "very dark", and seeing it on the Mac.** Metal SM5 on iOS has no Lumen, Nanite, Virtual Shadow Maps or ray tracing, so shadows get no bounced light. The packaged Mac app shows the same picture with `-ExecCmds="r.DynamicGlobalIlluminationMethod 0,r.ReflectionMethod 2,r.Shadow.Virtual.Enable 0,r.Nanite 0,r.VolumetricCloud 0"`, which makes the look tunable without a device.
- **Sky fill stands in for the bounce.** `+CVars=r.SkylightIntensityMultiplier=1.8` under `[IOS DeviceProfile]` in `Config/DefaultDeviceProfiles.ini` brought the lightness percentiles (10th/50th/90th) to 33/82/121 against the Mac's 38/77/118 with Lumen; 2.5 and 4 washed the shadows out. It cost no frame rate on the phone. A device profile cvar beats Scalability; a console or `-ExecCmds` value beats both.
- **Nanite meshes fall back to a coarse mesh where Nanite is off.** The importer's default fallback is a reduced mesh, which is what iOS draws. The fix, in editor Python, sets `nanite_settings.fallback_target = NaniteFallbackTarget.PERCENT_TRIANGLES` and `fallback_percent_triangles = 1.0` on every Nanite mesh (62 here) and saves; no measurable cost on the phone at this scene's size.
- **Volumetric clouds are off on iOS by engine default and expensive when on.** `BaseIOSEngine.ini` sets `r.VolumetricCloud.Support=0`; `r.VolumetricCloud.Support=1` under `[/Script/Engine.RendererSettings]` in `Config/IOS/IOSEngine.ini` brings them back (needs a recook).
  - On an iPhone 15 Pro Max in play: 59 fps without clouds over 26 s and no heat warning, about 21 fps with them (two runs) and "Temperature Changed: Serious" at 17 s.
  - `r.VolumetricCloud 0` at runtime, or per model in a `[iPhone15ProMax DeviceProfile]` section, turns them off without a rebuild of the code.
  - Cheaper cloud settings (`r.VolumetricCloud.ShadowMap 0`, `.SkyAO 0`, lower `.ViewRaySampleMaxCount`, `r.VolumetricRenderTarget.Scale 0.5`) are not measured yet.
