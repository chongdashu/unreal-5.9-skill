# iOS: building, signing, running on a phone, the look, and the App Store

Verified on the Epic launcher's 5.9.0 on a Mac (Xcode 26.2), from 11 to 17 November 2026, with two games: an iPhone 15 Pro Max (iOS 26.6) ran both, and an iPad Air (M4) on iPadOS 27 got as far as signing. The second game went through TestFlight to internal testers. Names starting `game.` stand in for the game's console variables: choose your own. The packaging command itself, and what every platform shares, is in `packaging.md`.

**Which renderer a phone gets.** With `bSupportsMetalMobileSM5=True` (section 1), the phone runs feature level SM5: its log says `rhifeaturelevel="SM5"` and `shaderplatform="METAL_SM5_IOS"`, and the engine maps SM5 and above to the deferred shading path (`GetFeatureLevelShadingPath` in `SceneUtils.h`, read in the 5.9 source). That is the desktop renderer without Lumen, Nanite, Virtual Shadow Maps or ray tracing, not the mobile renderer a web build gets. Fixes made for the web's mobile renderer (a sky dome, one directional light per channel) are not needed here: the second game switched its three web lighting fixes on only under the mobile renderer, and iOS did not need them (from the record). What the phone lacks is Lumen's bounce (section 4).

## 1. Building and signing

- **iOS needs the launcher's iOS option.** Without it `Engine/Binaries/IOS` does not exist. Epic Games Launcher, Library, the arrow beside Launch on the engine, Options, iOS; the editor must be closed.
- **The Mac's renderer (Metal SM6) cannot be built for iOS from the launcher install.** `bSupportsMetalMobileSM6=True` (Experimental; A17 Pro or M2 and newer) makes the build unzip `Engine/Binaries/ThirdParty/Apple/MetalShaderConverter/IOS/libmetalirconverter.embeddedframework.zip`, which the install does not contain: "Result: Failed (OtherCompilationError)".
  - `MetalShaderConverter.build.cs` only asks for it when bindless is on, but with `[ShaderPlatformConfig METAL_SM6_IOS] BindlessConfiguration=Disabled` the cook died with 366 errors in the engine's TSR shaders (`int16_t2` unknown).
  - A forum thread reports the same missing file on 5.8.
  - So no Lumen, Nanite, Virtual Shadow Maps or ray tracing on iOS from this install.
- **Metal SM5 on iOS built.** `bSupportsMetal=False`, `bSupportsMetalMobileSM5=True` under `[/Script/IOSRuntimeSettings.IOSRuntimeSettings]`, and `r.RayTracing=False` in `Config/IOS/IOSEngine.ini` (the project had it on for every platform): 849 packages cooked, 0 errors, a 500 MB `Binaries/IOS/<Project>.app`. Landscape only is the engine's default; `FrameRateLock` defaults to 30.
- **Signing with no new Apple setup.** `CodeSigningPrefix=com.<company>` under `[/Script/MacTargetPlatform.XcodeProjectSettings]` in `DefaultEngine.ini` gives the bundle ID `com.<company>.<Project>`; `CodeSigningTeam=<team id>` in the same section of `Config/UserEngine.ini` (ignored by Git) keeps the team out of the repo. Automatic signing then used the Xcode-managed wildcard profile ("iOS Team Provisioning Profile: *") already on the Mac.
- **A second device needs an Apple account in Xcode.** The wildcard profile on disk covered one device.
  - BuildCookRun's own xcodebuild uses `-destination generic/platform=iOS`, which never registers a device, so the profile stays as it was.
  - Re-running the last xcodebuild line from the UAT log (`UE_XCODE_BUILD_MODE=Package`) with `-destination "id=<device udid>" -allowProvisioningDeviceRegistration` is the route, and it needs an account under Xcode, Settings, Apple Accounts ("No Accounts" otherwise) whose developer agreement is current ("PLA Update available" otherwise; only the account holder can accept it, on developer.apple.com).
  - Not completed here: the agreement was still pending.
- **A device newer than Xcode.** An iPad Air (M4) on iPadOS 27 against Xcode 26.2: pairing worked (`xcrun devicectl manage pair`), the Developer Mode switch appeared in Settings only after pairing, and then the developer disk image would not mount ("The bundle image is missing the requested variant for this device").
  - Xcode, Settings, Components listed "Device Support for iPhone 17e, iPad Air 11-inch (M4), and iPad Air 13-inch (M4)"; the download leaves `~/Library/Developer/Packages/<Xcode build>/XcodeSystemResources.pkg`, which still has to be installed with an administrator password (Xcode asks, or `sudo installer -pkg <that file> -target /`).
  - After that it mounted. No Xcode update was needed.
- **The iOS Simulator is not a way to see the game.** With the launcher install, `Build.sh <Target> IOS Development -architecture=iossimulator` compiles the game module and then fails to link (`library 'ThirdParty/ICU/.../lib/IOS/Simulator/Release/libicu.a' not found`); a source checkout has those libraries. Even then MetalRHI marks SM5 and SM6 "not supported on simulator" and uses the mobile renderer (`SP_METAL_SIM`), so the picture and frame rate say nothing about a device. The failed try leaves empty folders under the engine's `Intermediate/Build/IOS/iossimulator`.

## 2. On the device

- **Putting it on a device without Xcode's window.** `xcrun devicectl list devices`, then `xcrun devicectl device install app --device "<device name>" Binaries/IOS/<Project>.app` and `xcrun devicectl device process launch --device "<device name>" --terminate-existing <bundle id> -- '-ExecCmds="game.Test.ShotAfter 20"'`. The inner double quotes must reach the device: without them the game got `-ExecCmds=game.Test.ShotAfter` and took the stray `20` for a map name ("Failed to enter /Game/Maps/..."; it then loaded the default map anyway). The 500 MB app installed in under a minute and the map was up 3 s after launch.
- **Wait for the phone to answer, not to be listed.** `devicectl list devices` showed a phone on Wi-Fi as "available (paired)" for a moment, and the install a few seconds later failed with CoreDeviceError 1011, "unable to locate a device". Poll `xcrun devicectl device info lockState --device "<name>"` until it succeeds and says `passcodeRequired: false`, then install. Seen on 5.9 with Xcode 26.2, 2026-11-16.
- **The device must be unlocked with its screen on.** Install fails with `kAMDMobileImageMounterDeviceLocked`, launch with "the device was not, or could not be, unlocked".
  - `xcrun devicectl device info lockState` reports `passcodeRequired: false` for a while after the screen sleeps, and an app launched then is sent to the background within a second ("Application will deactivate" in its log), as it is when the owner switches to another app.
  - Check the log for that line before reading anything into a missing screenshot.
- **Reading the game's files back.** `xcrun devicectl device copy from --device "<name>" --domain-type appDataContainer --domain-identifier <bundle id> --source Documents/<Project>/Saved --destination <folder>` brings the log (`Logs/<Project>.log`) and screenshots; `device info files` with the same domain options and `--recurse` lists them. In zsh, pass each option as its own word: options kept in one variable arrive as a single argument and devicectl prints its usage.
- **What the first device log showed.** About 53 to 60 frames per second on the title screen (from frame numbers and timestamps), and "Temperature Changed: Serious" 14 s after launch. The iPhone15ProMax device profile sets `r.MobileContentScaleFactor` to 2, so the backbuffer is 1864 x 860 on a 2796 x 1290 screen; safe-area numbers the engine reports are in those pixels (see the safe-area entry in `hud-and-input.md`, section 5).
- **"Temperature Changed: Bad" is iOS's Fair state, the mildest warning.** The engine maps `NSProcessInfoThermalStateNominal`, `Fair`, `Serious` and `Critical` to Good, Bad, Serious and Critical (`IOSAppDelegate.cpp`, read in the 5.9 source). A game on an iPhone 15 Pro Max reached Bad 10 to 20 s after launch.
- **Scripted steps on a phone.** A steps file copied into the app's container with `xcrun devicectl device copy to ... --domain-type appDataContainer --domain-identifier <bundle id> --source steps.txt --destination Documents/<Project>/Saved/steps.txt` is read by the game at `../../../<Project>/Saved/steps.txt`, and screenshots requested at `../../../<Project>/Saved/Screenshots/IOS/<name>.png` land in the same container, so the copy-back brings both. Simulated fingers in the steps (`game.Test.Touch` through `APlayerController::InputTouch`) drove a pause button and a menu tap on the device. Seen on 5.9, 2026-11-16.
- **Measuring frame rate on a device.** Pull the log back and divide the frame counter in the `[frame]` column by the timestamps, stopping at the first "Application will deactivate": a run where the owner touched the phone is not a measurement. Wait a few seconds before copying, or the log's tail is not flushed.
  - The `[frame]` column is the frame counter modulo 1000: count each time it goes down. A quiet game logs little, and two lines 16 to 20 s apart were seen; a gap could hide a whole wrap unless 1000 more frames would beat the frame-rate lock. A rate read this way first gave 2.9 and 6.5 fps for runs that were really 31 and 45. Seen on 5.9, 2026-11-16.
  - A timed measurement in the game (mean frame time by the wall clock over a set number of seconds) is the better number.
- **Keep the phone awake through an unattended run.** The engine turns iOS's idle timer back on after start-up, and two scripted runs locked about 30 s after the last real touch. The game's step-file hook now calls `FPlatformApplicationMisc::ControlScreensaver(FGenericPlatformApplicationMisc::EScreenSaverAction::Disable)` when a script starts and `Enable` when it ends.
- **A run that never started can look like a new result.** A phone reported itself unlocked with its screen off, the game never ran, and the copy-back brought the previous run's notes and screenshots as if they were new. Delete the earlier outputs in the container before launching, fail if the steps have not started within about 25 s, and read only files written by this run.
- **The first run stutters while pipeline states are made.** No pipeline cache ships by default: the first device log had "Encountered 50 PSO creation hitches so far (50 graphics, 0 compute). 4 of them were precached." at frame 518, 13 s after launch. Treat the first minute's frame rate as cold. No fix was tried.

## 3. Pricing a feature on a phone

- **On a phone locked to a frame rate, wall-clock frame time cannot price a feature.** In a sweep that switched parts of the look off one at a time, frame time read 16.67 ms on six rows of seven: the lock hid every saving. Average the game, draw, RHI and GPU times as `stat unit` reads them, count frames over 25 ms, hold the picture still (`slomo 0.01`, stepping by frames, since waits count game time), and put a base row between tests so heat drift shows in the base. Only switching the lens effect off moved GPU time, from about 18.6 to 16.85 ms. One run on one device: do not generalise past it.

## 4. The look on iOS

- **Why the phone looked "very dark", and seeing it on the Mac.** Metal SM5 on iOS has no Lumen, Nanite, Virtual Shadow Maps or ray tracing, so shadows get no bounced light. The packaged Mac app shows the same picture with `-ExecCmds="r.DynamicGlobalIlluminationMethod 0,r.ReflectionMethod 2,r.Shadow.Virtual.Enable 0,r.Nanite 0,r.VolumetricCloud 0"`, which makes the look tunable without a device.
- **Sky fill stands in for the bounce.** `+CVars=r.SkylightIntensityMultiplier=1.8` under `[IOS DeviceProfile]` in `Config/DefaultDeviceProfiles.ini` brought the lightness percentiles (10th/50th/90th) to 33/82/121 against the Mac's 38/77/118 with Lumen; 2.5 and 4 washed the shadows out. It cost no frame rate on the phone. A device profile cvar beats Scalability; a console or `-ExecCmds` value beats both.
- **Nanite meshes fall back to a coarse mesh where Nanite is off.** The importer's default fallback is a reduced mesh, which is what iOS draws. The fix, in editor Python, sets `nanite_settings.fallback_target = NaniteFallbackTarget.PERCENT_TRIANGLES` and `fallback_percent_triangles = 1.0` on every Nanite mesh (62 here) and saves; no measurable cost on the phone at this scene's size.
- **Volumetric clouds are off on iOS by engine default and expensive when on.** `BaseIOSEngine.ini` sets `r.VolumetricCloud.Support=0`; `r.VolumetricCloud.Support=1` under `[/Script/Engine.RendererSettings]` in `Config/IOS/IOSEngine.ini` brings them back (needs a recook).
  - On an iPhone 15 Pro Max in play: 59 fps without clouds over 26 s and no heat warning, about 21 fps with them (two runs) and "Temperature Changed: Serious" at 17 s.
  - `r.VolumetricCloud 0` at runtime, or per model in a `[iPhone15ProMax DeviceProfile]` section, turns them off without a rebuild of the code.
  - Cheaper cloud settings (`r.VolumetricCloud.ShadowMap 0`, `.SkyAO 0`, lower `.ViewRaySampleMaxCount`, `r.VolumetricRenderTarget.Scale 0.5`) are not measured yet.
- **Store screenshots need the scale raised for the run.** The iPhone 15 Pro Max profile draws at 1864 x 860 (`r.MobileContentScaleFactor` 2). `-dpcvars=r.MobileContentScaleFactor=3` at launch was meant to give the 2796 x 1290 the store asks for on a 6.9-inch phone. Not seen working: no frame of that width came back from a device.

## 5. The App Store and TestFlight

The engine-neutral steps are in two other skills: App Store Connect (the app record, TestFlight, the listing, privacy and review) in `asc`, and signing and the review rules that shape a build in `capacitor-ios`'s `references/app-store.md`. What follows was run with a 5.9 game, 16 and 17 November 2026; the store-side facts are as the session recorded them and were not re-checked.

- **An App Store archive.** `BuildCookRun -platform=IOS -clientconfig=Shipping -build -cook -stage -pak -package -distribution -archivedirectory=<path>/<Project>.xcarchive`, without `-archive`, archives straight to that path (otherwise to the newest archive in `~/Library/Developer/Xcode/Archives`). Automatic signing signs the archive for development; the distribution certificate and an App Store profile are needed only to export the `.ipa` (`xcodebuild -exportArchive`, or `asc xcode export`). A 5.9 Shipping app was 240 MB, against 513 MB for Development; nearly all of the difference is the executable (148 MB against 393 MB). Seen 2026-11-16.
  - **Set the build number yourself.** Left to the engine, `CFBundleVersion` is `<engine changelist>.0.<n>`, with n counted in `<Project dir>/Build/IOS/<dir name>.PackageVersionCounter`; a fresh worktree starts it again, so two uploads would carry the same number (four builds from fresh worktrees were all `60351404.0.2`). `-xcodebuildoptions="CURRENT_PROJECT_VERSION=<n>"` passes the setting to xcodebuild and the app's `CFBundleVersion` became `<n>`. The version, `CFBundleShortVersionString`, is `VersionInfo` under `[/Script/IOSRuntimeSettings.IOSRuntimeSettings]` (1.0 when unset).
  - The engine's Info.plist already declares `ITSAppUsesNonExemptEncryption` false, and `UIDeviceFamily` 1 and 2 (iPhone and iPad) unless `bSupportsIPad` is turned off.
  - **Icons and launch screen.** A project without its own ships the engine's: the Unreal logo as the icon, and "Unreal Engine" on black as the launch screen. In the 5.9 Xcode project a project's `Build/IOS/Resources/Assets.xcassets` replaces the engine's whole catalog, and `Build/IOS/Resources/Graphics/LaunchScreenIOS.png` (2048 x 2048, opaque; the engine's storyboard shows it) replaces the launch image (`XcodeProject.cs`). An `AppIcon.appiconset` with one 1024 x 1024 opaque image (`"idiom": "universal", "platform": "ios", "size": "1024x1024"`) was enough: Xcode made the 120 px iPhone and iPad sizes. Xcode re-encodes the PNGs it copies, so compare a built app's images after `xcrun -sdk iphoneos pngcrush -revert-iphone-optimizations`, not byte for byte. Seen 2026-11-16.
  - **Distribution signing with the App Store Connect CLI (`asc`), no Xcode account.** `asc certificates csr generate` writes a PKCS#8 key and a CSR; `asc certificates create --certificate-type DISTRIBUTION --csr <csr>` returns the certificate ("Apple Distribution: <company>"); `asc profiles create --profile-type IOS_APP_STORE --bundle <bundle id resource> --certificate <id>` and `asc profiles download` into `~/Library/Developer/Xcode/UserData/Provisioning Profiles/<uuid>.mobileprovision`. `security import <key> -t priv -f openssl` refused the PKCS#8 key ("Unknown format in import"); a `.p12` made with macOS's `/usr/bin/openssl pkcs12 -export` imported the pair in one go. Then `xcodebuild -exportArchive` with `method app-store-connect`, `signingStyle manual`, `signingCertificate "Apple Distribution"` and the profile by name re-signed a development-signed archive.
  - **An archive is tied to its team.** When App Store Connect is under a different team from the one development builds sign for, the export needs the archive made for the store's team (`CodeSigningTeam` in `UserEngine.ini` of the build copy). Automatic signing archived for it with the wildcard development profile Xcode had already made for that team.
  - **The first upload failed processing with error 90683 (missing purpose strings).** The 5.9 engine code in a plain game's iOS executable calls the microphone (`requestRecordPermission`, the record audio-session categories) and the camera (`AVCaptureDevice`, `requestAccessForMediaType`), and the generated Info.plist declares no `NS*UsageDescription`. `asc builds uploads view` gave only the code; Apple's email to the account holder named the key, `NSCameraUsageDescription` only. `strings` on the executable, searched for the APIs that need a purpose string, had found the camera calls and the microphone ones; the microphone string is not needed for this check. `AdditionalPlistData=<key>NSMicrophoneUsageDescription</key><string>...</string>\n<key>NSCameraUsageDescription</key><string>...</string>` under `[/Script/IOSRuntimeSettings.IOSRuntimeSettings]` is appended to the generated plist (`UEDeployIOS.cs`). Seen 2026-11-16.
  - **A Shipping build ignores `-ExecCmds`** (`UnrealEngine.cpp`, `#if !(UE_BUILD_SHIPPING)`) and writes no log, so the screenshot hooks used on Development builds do not run; check that it starts and stays up, and look at it.
- **A stopped upload still uses up its build number.** App Store Connect keeps the unfinished upload, and build numbers count up across versions, so the next upload takes the next number. One stopped part-way through as build 4; the next was 5.
- **Settle the version string before the first upload, across platforms.** A version record could be renamed with `asc versions update` while it was still being prepared for its first submission. Match the repository's release numbering: the iOS app first took a number a web build had already used. List the tags on every branch before choosing one.
- **TestFlight with `asc`.** `asc builds upload --wait` carried a build through processing (valid, exempt from encryption rules). Internal testers are invited only when the build is added to a group (`asc builds add-groups`). A user with the Developer role sees only the apps they are given (`asc users update --visible-app`), and adding a tester afresh with `asc testflight testers add --email --group` worked where reusing another app's tester record was refused.
- **Some steps are the website's or the account holder's.** The API could not create the app record or set a new app's first availability; `asc` 2.2.0 had no flag for the age rating's social-media question; App Privacy is set on the website. `asc validate` lists what is left (8 findings at the first try).
- **Try the store name in the New App form early.** A name held by an unreleased app was refused as "in use" although no app of that name shows in App Store searches. The listing's name can differ from the name under the icon.
- **Some choices are permanent.** The bundle ID cannot change once the App Store Connect record exists, and a build marked for iPhone and iPad (the engine's default) cannot drop iPad after release, so it needs iPad screenshots and a checked iPad layout. Decide both before the first upload.
- **Pass the `asc` profile on every call;** the default profile can be another account. The distribution private key `asc certificates csr generate` makes lives only in that Mac's keychain: export a `.p12` to sign elsewhere, and note the certificate's one-year expiry.
- **Check each generator's terms before a store release.** Plan tier and commercial use, revenue caps on generated music, whether a 3D model was made with paid or free credits, and whether the image service's terms say who owns the output (one did not). Record each against the game's asset list.
