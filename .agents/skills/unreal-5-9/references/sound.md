# Sound: importing it, and checking it without ears

Verified on Unreal Engine 5.9.0 (changelist 60351404, the launcher's install) on macOS 26.6, Apple Silicon (M4 Max), on 10 and 11 November 2026, while building a small sports game. Where a line comes from reading the engine source rather than from a run, it says so. Names starting `game.` or `GAME_` stand in for that game's console variables and actor labels: choose your own.

All of this ran in the game's dressed level on 5.9.0 (21 sounds: one-shots, an ambience loop, two music loops).

- **Import with the shipped tool.** `EditorToolset.SoundWaveToolset.ImportFile` takes `folderPath`, `assetName`, `sourceFile`, `bReplaceExisting`, `bSave` (the last two default to false) and declares wav, aif, aiff, ogg, flac, opus and mp3. 16-bit FLAC came in as 48 kHz Sound Waves with the source's length and channel count. `ExportWav` (`soundWave={"refPath": ...}`, `filePath`) writes one back out: four exports differed from their sources by at most 2 steps of 16-bit audio, so FLAC sources are safe and a third of the size of WAV in the repository.
- **Reading a Sound Wave in Python.** There is no `get_duration()`. `get_editor_property` works for `duration`, `num_channels`, `sample_rate`, `total_samples` and `looping`; `set_editor_property("looping", True)` then a forced save makes a loop.
- **Record what the game outputs.** The class is `unreal.AudioMixerLibrary` in Python (not `AudioMixerBlueprintLibrary`). During PIE: `start_recording_output(world, 40.0)`, let the game run, then `stop_recording_output(world, unreal.AudioRecordingExportType.WAV_FILE, "name", "folder")` writes `<Project>/Saved/BouncedWavFiles/folder/name.wav` (48 kHz stereo). It will not write anywhere else.
- **The editor mutes an unfocused game.** `BaseEngine.ini` sets `[Audio] UnfocusedVolumeMultiplier=0.0`, and `AudioDevice.cpp` multiplies the primary volume by it, so a PIE session driven over MCP while a terminal has focus is silent on the speakers. The probe set `au.DisableAppVolume 1` for the length of the recording and the recording had sound (peak -9.8 dBFS); recording without it was not tried. With it set, the game is also audible on the speakers, so say so before running it.
- **Game time and the recording drift.** The recording runs on real time; the event log on game time. Over 32 s the recording fell 0.68 s behind the log, 0.5 s of it in one editor hitch. Match each logged event to the nearest burst of sound and carry the offset forward; do not assume it is zero. Done that way, 19 of 19 logged swings, hits, serves and bounces had a burst at their moment.
- **Make the sound a probe.** The game's audio object counts every cue it is asked for in a `TMap<FName, int32>` debug property; Python reads it with `dict(audio.get_editor_property("plays").items())`. Count the request even when no sound is found, so "the game asked" and "it was heard" are separate checks.
- **C++ that compiled and played:** find a sound by name with `FPackageName::DoesPackageExist` before `LoadObject<USoundBase>` (a missing sound is then silence with no log warning); one-shots with `UGameplayStatics::PlaySound2D(WorldContext, Sound, Volume, Pitch)`; loops on components from `UGameplayStatics::CreateSound2D(WorldContext, Sound, 1, 1, 0, nullptr, false, false)` (last argument: do not auto-destroy), held in `UPROPERTY`s, with `SetVolumeMultiplier` each tick for cross-fades and ducking. Use a separate `FRandomStream` for pitch and variant choice: drawing from the game's seeded stream changes the rally.
- **Trap:** `AudioMixerLibrary.get_current_audio_output_device_name(world)` raises: it needs a delegate argument.
