# Packaging: a standalone Mac app, a Windows package, and what every platform shares

Verified on the Epic launcher's 5.9.0 on a Mac (Xcode 26.2), packaging two C++ games from 11 to 17 November 2026, and on a Windows PC for the second. iOS is in `ios.md`, the web in `web.md`. Names starting `game.` stand in for the game's console variables: choose your own.

## 1. Packaging and running a Mac app

- **The command.** `Engine/Build/BatchFiles/RunUAT.sh BuildCookRun -project=<abs .uproject> -platform=Mac -clientconfig=Development -build -cook -stage -pak -nop4 -utf8output -unattended` (add `-package` and use `-platform=IOS` for iOS, `ios.md`). On the first game the cook alone took 4 to 14 minutes; on the second, a whole first package took 107 s with a 48 s cook, and a fresh worktree after that 155 s (below). It compiles the editor module too, so close the editor on that checkout or use a worktree, and expect it to fail at once while another build holds the engine's build lock (`sharing-an-editor.md`, section 2).
- **Content loaded by name is not packaged.** A game that finds its art with `LoadObject` and path strings gives the cooker nothing to follow. Add `+DirectoriesToAlwaysCook=(Path="/Game/<folder>")` and `+MapsToCook=(FilePath="/Game/Maps/<map>")` under `[/Script/UnrealEd.ProjectPackagingSettings]` in `DefaultGame.ini`. Check what was cooked in `Saved/Cooked/<Platform>/<Project>/Metadata/ReferencedSet.txt`: a `find` for the files does not work, because they are in a container. The engine's basic shapes, loaded by path, were in both the Mac and the web cooks of the second game without being listed; why was not traced. If they are missing from that list, add `+DirectoriesToAlwaysCook=(Path="/Engine/BasicShapes")`.
- **The app to run is the staged one.** `Saved/StagedBuilds/Mac/<Project>.app` holds the content (under `Contents/UE`). The copy `-archive` writes, and `Binaries/Mac/<Project>.app`, are the program alone: they exit at once with "Failed to open descriptor file".
- **Run it from a shell with `-stdout -FullStdOutLogOutput`** and read the log from the pipe. `-abslog` wrote nothing.
  - The Development app is sandboxed, so its `Saved` folder is under `~/Library/Containers/<bundle id>`. A `find` there from the terminal hung until stopped, but reading by full path works: `~/Library/Containers/<bundle id>/Data/Library/Application Support/Epic/<Project>/Saved/`.
  - Or make an unsandboxed copy: `cp -Rc` the staged app, then `codesign --force --deep -s -` on the copy (no entitlements). It then saves under `~/Library/Application Support/Epic/<Project>/Saved`.
  - The first launch of a fresh copy printed nothing for over 30 s; the second ran normally.
- **A screenshot from a packaged game.** No editor, so no capture tool. A game CVar that calls `FScreenshotRequest::RequestScreenshot(true)` once after N seconds (`game.Test.ShotAfter` here), set with `-ExecCmds="game.Test.ShotAfter 12"`, wrote `Saved/Screenshots/Mac/ScreenShot00000.png` at the window's size. `-ExecCmds` values arrived 0.14 to 3 s after the map loaded, so a CVar read once at BeginPlay misses them. Several commands are separated by commas.
- **Give the run a size the screen can hold, and `-ForceRes`.** On a Mac, `-ResX=1920 -ResY=1080` alone was shrunk to fit the main display (1440 x 1080). With no size the game went full screen at a shape that was not 16:9 (1728 x 1084), and the screenshot hook wrote nothing ("Screenshot rect ... clamped" in the log). `-windowed -ResX=1920 -ResY=1080 -ForceRes` gave exactly 1920 x 1080; `-WinX/-WinY` (negative values allowed) place the window. Off screen, `-RenderOffScreen` (`capture-and-recording.md`, section 5).
- **A packaged desktop game draws below window size by default.** `stat unit` read "RenderRes: 72.9% (1400x788)" at 1920 x 1080 and 60.6% at 2560 x 1440: `r.ScreenPercentage` is 0 (automatic) and TSR scales up. Set `r.ScreenPercentage 100` to judge a look at full size; here that cost 68.5 ms against 51.2 ms a frame on a busy machine.
- **Nanite meshes went grey in the packaged game, not in the editor.** The log said "Material ... missing usage flag Nanite! Default Material will be used in game" for 16 materials.
  - The glTF importer turns Nanite on for every static mesh (62 of 62 here, 54,000 triangles in all) and parents every material to `/InterchangeAssets/gltf/M_Default` through `MI_Default_Opaque_DS`; that engine material has no Nanite flag, the editor sets it in memory, and a cooked game cannot.
  - Fix used: duplicate both engine assets into the game, `MaterialEditingLibrary.set_material_usage(copy, MaterialUsage.MATUSAGE_NANITE)`, and `set_material_instance_parent` the imported instances to the copy (41 instances, 0 warnings afterwards, and a capture of the packaged game showed the court and props in their own colours).
  - Turning Nanite off on the meshes would also do it.
  - Run a packaged build before trusting any look that was only seen in the editor.
- **Editing assets without a window.** `UnrealEditor-Cmd <.uproject> -run=pythonscript -script=<abs .py> -unattended -nosplash -AllowCommandletRendering` ran a script that changed and saved materials. With `-nullrhi` it failed: "this editor has no renderer, so materials can't be compiled". Neither `print` nor `unreal.log` reached the redirected output; write results to a file from the script. A Python error gives exit code 255.
- **Check a Mac build as a download arrives, but never launch the marked copy.** Run 2026-11-13 on 5.9 (macOS 26).
  - Unzip with `ditto -x -k`, add `com.apple.quarantine` with `xattr -r -w`, then `codesign --verify --deep --strict`. A valid ad hoc signature means Gatekeeper offers "Open Anyway" in System Settings. A broken one is reported as "damaged". `spctl -a` says "rejected" for any ad hoc app.
  - Starting the quarantined app's executable from a shell got it killed after 8 s with no output at all (exit 137), and may put a "Not Opened" box on the screen. Launch a second, unmarked unzip to prove the shipped app runs: it started, ran and quit cleanly in 20 s.
- **`syspolicy_check distribution` reports a fatal "Bad Load Command" on an Unreal Mac app.** Seen on 5.9's launcher install.
  - The executable carries search paths that point outside the bundle, at the engine install (`@executable_path/../../../`, `@loader_path/../../../../../../../../../Shared/Epic Games/UE_5.9/...`).
  - Every library it needs was also inside the bundle, under `Contents/UE/`, so the app runs without an engine install. The one not bundled, `libonnxruntime`, is weak-linked.
  - Only notarisation needs these paths gone (`install_name_tool -delete_rpath`, before re-signing); not tried here.
- **A fresh worktree packaged in 155 s.** BuildCookRun with `-build -cook -stage -pak` on a project of about 730 cooked packages, after earlier builds had filled the engine's shared cache. The 1,000 MB app zipped to 502 MB with `ditto -c -k --keepParent`.
- **Keep the agent plugins out of the game.** `ModelContextProtocol` has Runtime modules. Give it, `AllToolsets` and `PythonScriptPlugin` `"TargetAllowList": ["Editor"]` in the `.uproject`; the editor still loads them. A Development package still mounts `PythonScriptPlugin`, `ToolsetRegistry` and `Fab` (no `LogPython` line, no MCP server); why was not established.
- **Lines every 5.9 package prints, so a check flags only new ones.** Packaging: one warning, "Plugin 'Fab' does not list plugin 'ToolsetRegistry' as a dependency". A packaged Development run: 13 to 15 warnings, all `LogToolsetRegistry` "Cannot register Toolset SequencerScripting.… no baked manifest" or "Failed to find object … SequencerScripting.ToolsetManifest", on Mac and Windows alike, plus "AudioUnit: Error querying Sample Rate" on Mac and, on Windows, `LogWindows` lines that fail to load `WinPixGpuCapturer.dll`, `VtuneApi.dll`, `VtuneApi32e.dll` and `aqProf.dll` (not warnings). The game ran clean with all of them.
- **Before the first public build, set the names a player sees and the map they start on.** A project left on its defaults ships as `<Project>.app` with the bundle ID `com.YourCompany.<Project>`, and as `<Project>.exe`. Set `GameDefaultMap` to the game's own opening scene: a Shipping build opened on the development scene list.
- **Read a size limit against the file that is uploaded.** The second game's Development packages were just over 1 GB unpacked (Mac 1,000,783,904 bytes, Windows 1,041,253,360) and about half that zipped (502 MB and 471 MB). An upload limit such as itch.io's 1 GB counts the zip.

## 2. A Windows package of a game written on a Mac

A Mac cannot package for Windows; the project goes to a Windows PC with Visual Studio 2022's C++ tools and the launcher's 5.9, and `RunUAT.bat BuildCookRun -platform=Win64` runs there. Run on 15 November 2026 for a game jam that required a Windows package, on the owner's PC (24 cores, an RTX 4060 Laptop GPU). Package for the required platform early: here the requirement was found three days after it was posted, one day before the deadline.

- **Send the PC a kit, not a clone of the repository.** A zip of `git archive <rev> game`, the PowerShell scripts, a version file and a README (about 65 MB) needs no Git on the PC. Have each script find the kit from its own folder (`$PSScriptRoot`) and accept `-Engine` and `-Out`, so it still runs after the owner unzips it somewhere else: the owner asked whether the repository had to be cloned on the PC, then moved the kit twice. Say up front what the PC does not need, and let the owner skip a step already done, such as an install.
- **Script the toolchain.** Visual Studio 2022 Community with the `NativeGame` and `NativeDesktop` workloads (`vs_community.exe --passive --wait`), found afterwards with `vswhere -requires Microsoft.VisualStudio.Component.VC.Tools.x86.x64`; only the Windows target platform from the launcher. Call `RunUAT.bat` through a generated `.bat`, so paths with spaces keep their quotes and the build's error lines do not stop PowerShell; `Unblock-File` the kit and run the scripts with `-ExecutionPolicy Bypass`.

- **MSVC rejects code that the Mac's Clang accepts.** A local variable with the name of a member the class inherits from the engine, `const float Canvas = ...` inside an `AHUD` subclass, is MSVC warning C4458, and Unreal builds treat shadowing as an error: `error C4458: declaration of 'Canvas' hides class member`. Clang compiled the same file with Unreal's `-Wshadow`, and with `-Wshadow-all` said nothing about that line (it only tripped on an engine header), so a Mac build cannot catch it. Do not name locals after engine members (`Canvas`, `Owner`, `Controller`, `Instigator`, `World`, `Mesh` and the like).
- **A Win64 package takes minutes once the tools are in.** Compiling a 14-file game module took 45 s with Unreal Build Accelerator before the error above stopped it. The first successful BuildCookRun took 160 s (compile 19.1 s, cook 71.6 s, with the PC's shader cache already partly warm), and later packages 72 to 90 s. The errors reach the console and the log under `%APPDATA%\Unreal Engine\AutomationTool\Logs\`.
- **A staged Win64 build has two executables.** The top `<Project>.exe` (174 KB) is a bootstrap that starts `<Project>\Binaries\Win64\<Project>.exe` (345 MB). A check must wait for every process of that name; a scripted run can start the inner one. A Development package resolves its `Saved\` folder inside the package (`<Project>\Saved\`); also look in `%LOCALAPPDATA%`.
- **`-prereqs` stages Microsoft's `vc_redist`, not `UEPrereqSetup`.** It put `vc_redist.x64.exe` and `vc_redist.arm64.exe` beside the game, so a check that looked for `UEPrereqSetup*.exe` called the prerequisites missing.
- **Check it as a player gets it.** Unzip, start the top executable with the same screenshot hook the Mac uses (`-windowed -ResX=1920 -ResY=1080 -ForceRes -nosplash -unattended -nosound -ExecCmds="game.Test.ShotAfter 10, game.Test.QuitAfterShot 1"`), read the log, look at the frame: 16 s, a 1920 x 1080 frame, 0 errors. Then a scripted run of the inner executable: 62 s, four frames, 8.90 to 9.63 ms a frame.
- **Move a build between machines as its zip, and compare its SHA-256 with the package receipt.** A cloud-drive download of the release folder came back split, with no game executable in the unzipped part, while the zip itself matched the receipt. A hash names one package run, not a revision: three packages of one commit gave three hashes.
- **A cloud Windows PC: check the GPU quota first.** The account's quota for GPU instances was 0, and raising it is a request with no stated wait. Packaging needs no GPU, so a compute instance can package, and a check with no GPU can fall back to `-nullrhi` (the game runs, no frames). This route was written and not run; the owner's own PC was used.
